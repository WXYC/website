<p>A statically generated site for WXYC. Built using the frontend framework React, NextJs as a static site generator and TinaCMS as a Git-based content management system. Styled using TailwindCSS, with help from the MUI Joy UI component library on implementing breadcrumbs and Headless UI on implementing dropdown menus. Deployed to Github Pages.</p>

<p>Supports content management for the radio station's blog and for an archive of the radio station's specialty shows and live events. Very much a work in progress!</p>

<h3>Playlist archive (<code>/playlists/archive</code>)</h3>
<p>Public, week-at-a-time browse of every show WXYC has logged, back to at least November 2004. Successor to <code>wxyc.info/playlists/radioWeek</code>, which went dark at the 2026-09-07 tubafrenzy cutover (<a href="https://github.com/WXYC/wiki/issues/93">WXYC/wiki#93</a>).</p>
<ul>
<li><b>Data source</b>: Backend-Service <code>GET /flowsheet/range?start=&amp;end=</code> (epoch milliseconds, half-open <code>[start, end)</code>, 8-day ceiling). Contract lives in <code>wxyc-shared/api.yaml</code>. Override the origin at build time with <code>NEXT_PUBLIC_WXYC_API_URL</code>; it defaults to <code>https://api.wxyc.org</code>.</li>
<li><b>Client-side only.</b> This site is a static export, so there is no SSR and no <code>getStaticPaths</code> over a 2.6-million-row table. The week lives in <code>?week=YYYY-MM-DD</code> (always a Monday) so a week is linkable, and the fetch happens after hydration.</li>
<li><b>Weeks and days are Eastern</b>, not UTC and not browser-local &mdash; see <code>lib/easternTime.js</code>. Day and week bounds are computed by calendar arithmetic rather than by adding fixed millisecond offsets, because the spring-forward week is 167 hours and the fall-back week is 169.</li>
<li><b>Playlists are collapsed by default.</b> A week is 2,300&ndash;2,800 entries and 470&ndash;640&nbsp;KB gzipped, so each show is a <code>&lt;details&gt;</code>: the schedule is always visible and the rows only get laid out when opened. Note that the rows are still <i>built</i> &mdash; <code>&lt;details&gt;</code> skips layout, not DOM construction. Deferring construction to first open is the next lever if the page ever feels slow on a phone.</li>
<li><b>Entries are ordered by <code>play_order</code>, not by arrival.</b> The endpoint returns rows in <code>add_time</code> order, and the two disagree whenever a DJ enters a row after the fact &mdash; 88 times across 36 of the 54 shows in a sampled production week. Ordering by arrival strands retroactively-added hour breakpoints in the middle of a later hour.</li>
<li><b>Past weeks are cached in memory</b> (<code>lib/weekCache.js</code>). The endpoint sends no <code>Cache-Control</code>, so without this every Previous/Next click and every browser Back re-downloads half a megabyte. The week in progress is deliberately never cached.</li>
<li><b>The requested week is clamped</b> to <code>[2004-11-01, current week]</code>. <code>?week=</code> accepts anything, and <code>&lt;input type="date"&gt;</code> reports every keystroke of a typed year (editing to 2026 emits 0002, 0020, 0202 first), so without a clamp each of those becomes a live range query against a 2.6-million-row table.</li>
</ul>

<h3>Live playlist (<code>/playlist</code>)</h3>
<p>Public view of the most recent flowsheet entries, refreshing while the tab stays open. Successor to <code>wxyc.info/playlists/recent</code>, which goes dark at the 2026-09-07 tubafrenzy cutover (<a href="https://github.com/WXYC/wiki/issues/93">WXYC/wiki#93</a>).</p>
<ul>
<li><b>Data source</b>: Backend-Service <code>GET /flowsheet</code>, through <code>lib/flowsheet.js</code> &mdash; <code>?page=0&amp;limit=50</code> for the landing view, <code>?shows_limit=1&amp;page=N</code> for one set. Distinct from the archive's <code>/flowsheet/range</code>: neither branch returns a separate <code>shows</code> array, so there is no grouping step. The two branches do not share a response shape, and the bullet below spells out how they differ &mdash; the landing view gets a flat <code>entries</code> array plus pagination metadata and the on-air DJ; a set gets a bare array and none of that. Contract lives in <code>wxyc-shared/api.yaml</code>. Override the origin at build time with <code>NEXT_PUBLIC_WXYC_API_URL</code>; it defaults to <code>https://api.wxyc.org</code>.</li>
<li><b>Client-side only</b>, for the same reason as the archive: a static export has no SSR and no server to poll from, so the fetch happens in the browser, on an interval, for as long as the tab stays open.</li>
<li><b>Entries are ordered by <code>show_id</code> then <code>play_order</code>, both descending, then <code>id</code> descending</b> &mdash; most recent show first, and within a show by the DJ's stated air order rather than the order the endpoint returned them in (insertion order). The endpoint returns rows newest-inserted-first, and a DJ who enters a row after the fact gets a row whose <code>id</code> says "just now" but whose <code>play_order</code> says otherwise; rendering in insertion order strands it in the wrong place. The <code>id</code> tie-break exists because <code>play_order</code> can legitimately collide &mdash; the tubafrenzy webhook and the dj-site live-insert path assign it independently with no per-show UNIQUE constraint &mdash; matching how Backend's own <code>getEntriesByShow</code> breaks the same tie. See <code>compareEntriesByAirOrderDesc</code> in <code>lib/flowsheetRange.js</code>, shared with the archive page's own <code>play_order</code> rule.</li>
<li><b>The search box hands off; it does not search here.</b> Submitting sends the query to <code>/airplay-search?q=&hellip;</code> rather than filtering the rows already on screen. A box that filtered fifty rows while looking like it searched WXYC's airplay is the more damaging of the two ways to get this wrong, and handing off keeps one search implementation &mdash; everything <code>lib/flowsheetSearch.js</code> knows about field-filter syntax, the capped <code>total</code> sentinel and the paging-depth cliff applies to a search started from here, for free. An empty submit does nothing: pressing Enter in a box you have not filled in is not a request to leave the page.</li>
<li><b>Two views, two units, and the controls say which is which.</b> The landing view is a fixed window of the most recent rows and spans several sets &mdash; which is why it needs a cross-show sort at all. <code>?set=N</code> is one DJ's show end to end, whatever length that happens to be. Calling both "page" and putting Previous and Next either side would imply a sequence they do not share: stepping back from the landing view lands on a set whose last rows are already on screen above it. So the landing view offers one way out, <i>Earlier sets</i>, and a set offers <i>Previous set</i> plus a control that says <i>Now playing</i> rather than calling the landing view the next set. The controls sit above the list and outside every state branch: a set can run to several hundred rows, so navigation below the fold is navigation nobody finds, and rendering them per-branch left the loading state &mdash; the one you most want to leave &mdash; with no way out.</li>
<li><b>Set pagination is <code>GET /flowsheet?shows_limit=1&amp;page=N</code></b>, which Backend routes to <code>getNShows(n, page)</code> &mdash; <code>ORDER BY shows.id DESC OFFSET page &times; n LIMIT n</code> &mdash; and then returns every entry belonging to the shows it selected. Two things about that branch differ from the default one and a client written against the envelope gets both wrong: it responds with a <b>bare array</b> (no <code>total</code>, no <code>page</code>, no <code>on_air</code>), and it responds <b>404</b> for a set with no rows.</li>
<li><b>A 404 there is not an error and not the end of the archive.</b> It means "this set has no rows", which covers both a show that was opened and closed with nothing logged and paging past the oldest show &mdash; and the status cannot tell them apart. So it renders as a sentence, not an alert, and it never disables the navigation: a button disabled on that signal would turn one empty show in the middle of the archive into a permanent wall telling the reader they had reached 2004.</li>
<li><b>A set reads newest-first, unlike the same show on the archive page.</b> That is deliberate, and it is the one place these two surfaces disagree about a show. <code>groupRangeByDay</code> sorts a show's entries ascending for the archive, and dj-site's show view does the same, because a set read on its own reads in the order it aired. But this page's landing view is the most recent rows of the flowsheet with the newest at the top, and a reader stepping back one set should not have the list invert under them. The reading direction belongs to the page, not to the set.</li>
<li><b>Only the landing view polls.</b> An archived set cannot change, so re-requesting it every minute would be pure waste; dj-site caches the equivalent read for ten minutes for the same reason.</li>
<li><b>The set header is derived from the set's own rows.</b> That endpoint branch returns no <code>shows</code> metadata at all, so the DJ and the air times come from the <code>show_start</code> / <code>show_end</code> markers &mdash; the second independent signal <code>api.yaml</code> names for a show's extent. Resolution order is sign-on, then sign-off, then any other marker row: a <code>dj_join</code> names the guest who arrived partway through someone else's set, so reading it first would caption the show with the wrong person. Track rows are never consulted; they carry no <code>dj_name</code> on the V2 wire.</li>
<li><b>Every track row is dated <code>MM/DD/YYYY</code> on the station clock</b>, in a trailing column. The list runs back across set boundaries and past midnight, so without it a reader scrolling down has no way to tell which day a play belongs to. Eastern, not the reader's zone: a play logged at 11:06&nbsp;PM in Chapel Hill is already the next day in UTC, and dating it by the browser files it under a day WXYC did not broadcast it. The column is last rather than first so the row marks keep the leading column their key points at. It is not the same rendering as <code>/airplay-search</code>'s <code>Played</code> column, which sits fifth of six, left-aligned, as a long <code>July 21, 2026, 11:47 AM</code>. A row whose <code>add_time</code> is unusable gets an empty cell rather than a placeholder to decode. The four-digit year is deliberate: dj-site renders <code>M/D/YY</code> over an archive it advertises as "November 2004 to present", and two digits are ambiguous over a span that long.</li>
<li><b>Separator rows still span every column, date included.</b> They are read as a band (see <i>Separator rows</i> above), and cutting a date cell out of the left edge would reopen the gap that fill exists to close. Two of them carry their timing in their own text &mdash; a sign-on names its clock time, a breakpoint names its hour &mdash; and two do not: <code>dj_join</code> and <code>dj_leave</code> say who arrived or left and nothing about when. That gap is left open rather than reopening the band for the two rarest row types on the page.</li>
<li><b>A failed poll keeps the last good playlist on screen</b> rather than replacing it with an error: the table is still true, just stale. A "Last updated HH:MM &mdash; couldn't refresh" notice and a Retry button appear alongside it so the page is never silently frozen; only a failure on the very first load (nothing to show yet) replaces the page with a full error state.</li>
<li><b>Polling pauses while the tab is hidden</b> — checked both at mount and on every subsequent visibility change, so a tab opened directly in the background never fetches at all until it is actually shown — and catches up with one fetch when it becomes visible again, rather than continuing to poll a tab nobody is looking at. The response is ~51&nbsp;KB with <code>Cache-Control: no-cache</code>, and a tab left open for a workday would otherwise issue roughly 1,440 requests for ~73&nbsp;MB.</li>
<li>Each poll aborts any still-in-flight one before starting, so a slow earlier response landing after a faster later one cannot overwrite fresher data with stale.</li>
</ul>

<h3>Airplay search (<code>/airplay-search</code>)</h3>
<p>Public search over WXYC's full airplay history, back to at least November 2004. Successor to <code>wxyc.info/playlists/searchPlaylists</code>, which went dark at the 2026-09-07 tubafrenzy cutover (<a href="https://github.com/WXYC/wiki/issues/93">WXYC/wiki#93</a>).</p>
<ul>
<li><b>Data source</b>: Backend-Service <code>GET /flowsheet/search?q=&amp;page=&amp;limit=</code>. Contract lives in <code>wxyc-shared/api.yaml</code>. An empty or omitted <code>q</code> is a supported request, not an edge case &mdash; it is what makes the backend serve its most-recent-tracks default, which is this page's landing view. Same <code>NEXT_PUBLIC_WXYC_API_URL</code> build-time override as the archive page.</li>
<li><b>The query is in the URL as <code>?q=</code>; the page number is not.</b> A query is a durable thing to address, and putting it there is what makes a result set something a listener can send to somebody &mdash; including the live playlist page, whose search box is a link into this one. A page of a query is not durable: <code>MAX_REACHABLE_PAGE</code> clamps depth, and the depth at which this endpoint starts failing moves with database load, so a link to page 380 of a broad search is a link that works until it doesn't. A play's date is rendered numerically here too (<code>07/21/2026, 11:47 AM</code>), matching the live playlist's column, because the two pages became one journey the moment the playlist grew a search box that hands off to this one; the time stays, since a search result arrives with none of the context a playlist row has. The query is written with <code>replace</code>, not <code>push</code> &mdash; the box is a live filter, and one history entry per settled keystroke would make Back mean "delete the last few characters" over and over instead of leaving the page. Results still live in component state; this site is a static export, so there is no SSR to fetch behind.</li>
<li><b>The first fetch waits for the router.</b> On a static export the query string is empty on the first render and arrives after hydration, so searching before reading it would spend a request on the landing view for every shared link and briefly show the wrong answer.</li>
<li><b><code>total</code> is a capped sentinel, not a count.</b> The backend's <code>COUNT_CAP</code> is 10000; any query matching more rows &mdash; including the empty-query landing view, against the ~2.6-million-row table &mdash; comes back with <code>total</code> pinned at exactly 10001. Render it raw and the default state of the page prints a false number to every visitor. <code>formatSearchTotal</code> shows anything past the cap as an open-ended <code>10,000+</code> instead.</li>
<li><b>Reachable pages are clamped well short of where the endpoint actually fails</b> (<code>MAX_REACHABLE_PAGE</code>, currently 99). Deep <code>OFFSET</code> pages on this endpoint approach and can exceed the backend's 5-second statement timeout, and the page where that happens is not a fixed number &mdash; it moves with database load, so no constant can safely sit right at the edge. The clamp is set at roughly a quarter of the smallest offset ever observed to survive, trading away some reachable depth for headroom against that drift, rather than being tuned close to a boundary that has already been seen to move. The actual fix is switching to the endpoint's cursor-paging mode, which is O(limit) instead of O(page&nbsp;&times;&nbsp;limit) and has no such cliff; raising this constant instead of making that switch just moves the same failure further out.</li>
</ul>

<h3>Separator rows on the playlist pages</h3>
<p>Between the track rows, <code>/playlist</code> renders the flowsheet's non-track entries &mdash; breakpoints, talksets, free-text messages, a guest DJ arriving, and the sign-on and sign-off that delimit each set. They span the whole table rather than filling the track columns. (<code>/playlists/archive</code> renders the same rows minus the two show delimiters, because its show header already says who signed on and when.)</p>
<ul>
<li><b>Four of these entry types carry no <code>message</code> at all.</b> <code>show_start</code>, <code>show_end</code>, <code>dj_join</code> and <code>dj_leave</code> name a DJ in <code>dj_name</code> instead &mdash; Backend's V2 projection emits <code>dj_name</code> and, for the two delimiters, a <code>timestamp</code>, and nothing else. A <code>message ?? entry_type</code> fallback therefore prints the bare wire token, which is what put "show start" and "show end" around every set on this page (<a href="https://github.com/WXYC/website/issues/241">#241</a>). <code>describeNonTrackEntry</code> in <code>lib/flowsheetRange.js</code> is the single place that maps an entry to its line, for every surface.</li>
<li><b>A set opens with "&lt;dj&gt; signed on at 6:58 PM" and closes with "&lt;dj&gt; signed off at 9:02 PM".</b> The wording is the station's own, from tubafrenzy's recent-entries page (<code>START OF SHOW: DJ Starcross'd SIGNED ON at 6:58 PM (6/4/25)</code>) minus the shouting, and it matches dj-site's Classic flowsheet. The clock time stays in the text because these rows span the table and so are the one row type that cannot carry a date cell of its own; the date is not repeated, since the rows around it carry that.</li>
<li><b>They are no longer uppercased.</b> The <code>uppercase</code> class suited these rows when their entire vocabulary was station tokens &mdash; <code>TALKSET</code>, <code>--- 7:00 PM BREAKPOINT ---</code> &mdash; which arrive already capitalised in the data and read the same either way. It stopped suiting them once they carried DJ handles: a handle is a chosen name, and <code>stink</code> rendered as <code>STINK</code> or <code>DJ Starcross'd</code> as <code>DJ STARCROSS'D</code> is not that person's name. Dropping the class changes nothing about the token rows and stops the page shouting at the DJs.</li>
<li><b>They are filled <code>bg-white/10</code>, not <code>bg-white/5</code>.</b> Over the opaque panel (see <i>Reading over the animated background</i> below) a 5% white fill is a 13/255 grey &mdash; present in the DOM, absent to the eye. On a long list these rows are the only structure there is, so the fill has a legibility floor of its own, checked in <code>__tests__/playlistContrast.test.js</code>. WCAG has nothing to say about it: 1.4.3 governs text against its background, and a band that fails to read as a band still passes.</li>
<li><b>An unresolved handle arrives as the empty string, not <code>null</code></b> &mdash; the same projection defaults it with <code>entry.dj_name ?? ''</code>. Both fall through to "Signed on" / "Signed off", which says the set changed hands without inventing a name for who was holding it.</li>
</ul>

<h3>Row marks on the playlist pages</h3>
<p>A track row on <code>/playlist</code> and <code>/playlists/archive</code> can carry two marks in its leading column, with a key above the list saying what they mean: <b>&#9679; in rotation</b> and <b>&#9733; listener request</b>. <code>pages/airplay-search.jsx</code> shows neither and has no key.</p>
<ul>
<li><b>The rotation bin is deliberately not published.</b> <code>rotation_bin</code> arrives in the envelope as the library's own H/M/L/S weighting (<code>RotationBin</code> in <code>wxyc-shared/api.yaml</code>: Heavy, Medium, Light, Single). That is internal bookkeeping about how hard a record is being pushed, not a question a listener reading a playlist is asking, so the page renders the binary fact &mdash; this was in rotation &mdash; and drops the letter (<a href="https://github.com/WXYC/website/issues/236">#236</a>). There is no C bin; if you see one, something invented it.</li>
<li><b>Both flags share one column.</b> A request used to render as the literal text <code>(request)</code> after the record label, in a different vocabulary from the rotation mark and three columns away from it. Both are facts about the same play and now sit together (<a href="https://github.com/WXYC/website/issues/239">#239</a>).</li>
<li><b>Each mark keeps its own <code>sr-only</code> text</b> rather than relying on the key. The key is a visual aid, and a screen reader working through a table has no way back up the page to interpret a bare glyph &mdash; worse here than elsewhere, because the header row on these tables is itself <code>sr-only</code>.</li>
<li><b>The key renders only alongside a list.</b> An empty week or a failed fetch does not explain marks it is not showing.</li>
</ul>

<h3>Reading over the animated background</h3>
<p>Every page paints a WebGL "lava lite" background (<code>components/LavaLiteBackground.jsx</code>, mounted once in <code>_app</code>). Behind a headline that is fine; behind the three playlist surfaces &mdash; hundreds of rows of small type &mdash; it was not. Listeners reported the lists as "nearly impossible to read", and the station advisor relayed it as a consensus rather than one person's taste (<a href="https://github.com/WXYC/website/issues/234">#234</a>). Two separate problems were inside that report, and each has its own fix.</p>
<ul>
<li><b>Contrast: the playlist pages sit on an opaque surface</b> (<code>components/ReadableSurface.jsx</code>). Text over a moving gradient has no fixed contrast ratio &mdash; legibility becomes a property of whichever frame you looked at. The surface makes the backdrop a constant, so a ratio can be stated at all; the background still surrounds the page through the gutters, header and footer. It is deliberately <i>fully</i> opaque rather than <code>bg-black/95</code>: any alpha leaves contrast a function of the frame underneath, which is the dependency the surface exists to remove.</li>
<li><b>Contrast: text tints are floored at <code>text-white/50</code></b> (5.28:1 on the bare panel, 5.22:1 over the <code>bg-white/10</code> separator fill, against the 4.5:1 AA requirement for body copy). <code>text-white/40</code> is 3.66:1 and fails even on pure black, so it is not available on these pages. <code>__tests__/playlistContrast.test.js</code> computes the ratio for every tint the three pages use and fails the build on anything below AA &mdash; a source-level check, since jsdom computes no colours. It reads each page's fills out of that page's own source rather than holding a list of them: a hard-coded backdrop that has gone stale is invisible, because it still produces a plausible ratio for every tint.</li>
<li><b>Motion: <code>prefers-reduced-motion: reduce</code> freezes the background</b> rather than blanking it &mdash; one static frame, no <code>requestAnimationFrame</code> loop, so the station's identity survives and the movement does not. The preference is read through <code>lib/usePrefersReducedMotion.js</code>, which uses <code>useSyncExternalStore</code> so the answer is right on the first render (a hook that corrected itself in an effect would let one frame of animation through) and follows the OS setting if it changes mid-session. Because a resize clears the WebGL drawing buffer and a frozen background has no next frame to repaint it, the resize handler redraws the still frame itself.</li>
</ul>

<h3>Previewing the playlist pages locally (<code>scripts/mock-backend.py</code>)</h3>
<p>The three playlist surfaces read <code>api.wxyc.org</code> from the browser, and that origin's CORS allowlist does not include localhost &mdash; a dev server gets <code>Access-Control-Allow-Origin: https://dj.wxyc.org</code> back, the browser drops the response, and every page renders its error state. So <code>npm run dev</code> alone cannot show you a playlist with anything in it. <code>scripts/mock-backend.py</code> serves the same endpoints from localhost with permissive CORS:</p>
<pre><code>python3 scripts/mock-backend.py            # terminal 1, port 8899
NEXT_PUBLIC_WXYC_API_URL=http://127.0.0.1:8899 npm run dev   # terminal 2</code></pre>
<p>Standard library only, read-only, bound to <code>127.0.0.1</code>, and it invents its own rows &mdash; it never touches a real database. Artists come from the org's canonical WXYC example data (see the "Example Music Data" section of the org <code>CLAUDE.md</code>), including the three diacritic-bearing names, so the pages get exercised against text they will really render.</p>
<ul>
<li><b>It reproduces the awkward parts of the contract on purpose.</b> <code>?shows_limit=1</code> answers with a bare array rather than the <code>{entries, total, page, &hellip;}</code> envelope, and answers <code>404</code> for a set with no rows &mdash; both true of the real endpoint, and both driving UI you cannot otherwise see. Set 3 is empty deliberately, and so is anything past <code>MOCK_SET_COUNT</code>, so the mid-archive and past-the-end cases are each reachable; the endpoint cannot distinguish them, which is the whole point of how the page handles them.</li>
<li><b>CORS is attached in <code>end_headers</code>, so it lands on every response including errors.</b> Not a detail: <code>BaseHTTPRequestHandler.send_error</code> composes its own response and ignores headers set elsewhere, so a bare 404 makes the browser refuse to hand the response to <code>fetch</code> at all. A page that distinguishes "this set is empty" from "the request failed" can then only ever show the second, which reads exactly like a bug in the page and is not one. The real service puts CORS on error responses too.</li>
<li><b>Search filters.</b> Free text plus <code>artist:</code> / <code>song:</code> / <code>album:</code> / <code>label:</code> / <code>dj:</code> and <code>AND</code>. It does <i>not</i> implement <code>OR</code>, <code>NOT</code>, quoting or precedence &mdash; if a query exercising those behaves oddly, that is this file's limit, not the page's. An empty query returns the capped <code>total: 10001</code> sentinel the real endpoint returns, so that rendering path is exercised too.</li>
<li><b>Dates are always today.</b> Rows are generated relative to the current time, so the date column and day headings will not show you a realistic spread of history.</li>
</ul>

<h3>DNS &amp; hosting (do not "fix" the Pages domain warning)</h3>
<p><code>wxyc.org</code> and <code>www.wxyc.org</code> are proxied through Cloudflare (orange-cloud) rather than pointing their DNS records directly at GitHub Pages. Cloudflare forwards the <code>Host</code> header to GitHub Pages as the origin, so the site is still built and served by this repo's Pages deploy exactly as before &mdash; Cloudflare just sits in front of it (this is what lets us attach edge Workers to the apex).</p>
<p>Because the public A/AAAA records no longer resolve to GitHub's Pages IPs (they resolve to Cloudflare's edge), <b>repo Settings &rarr; Pages will show a warning that the custom domain's DNS does not point at GitHub Pages.</b> This warning is expected and cosmetic &mdash; the site works. <b>Do not change the DNS records back to GitHub's IPs, and do not clear the custom-domain field in Settings &rarr; Pages</b> (the custom domain lives only there; there is no <code>CNAME</code> file in the repo). Reverting either would break the Cloudflare proxy in front of the apex. If you need to take Cloudflare out of the path, toggle the apex + <code>www</code> records from orange (Proxied) back to gray (DNS only) in the Cloudflare dashboard.</p>

<h3>TLS &amp; certificates (do not set SSL/TLS mode to Full (strict))</h3>
<p>There are <b>two</b> certificates in front of this site. The <b>edge certificate</b> is Cloudflare's (Google Trust Services) and is what browsers actually see; Cloudflare renews it automatically and it has never been a problem. The <b>origin certificate</b> is the Let's Encrypt certificate GitHub Pages manages for the custom domain, presented to Cloudflare when it fetches from the origin. Since the proxy went in front of the apex the origin certificate is invisible to browsers &mdash; read it by connecting to a Pages IP directly rather than to <code>wxyc.org</code>: <code>echo | openssl s_client -servername wxyc.org -connect 185.199.108.153:443 2&gt;/dev/null | openssl x509 -noout -issuer -dates</code>.</p>
<p><b>The origin certificate's renewal is currently broken.</b> <code>GET /repos/WXYC/website/pages</code> reports <code>https_certificate.state: "bad_authz"</code> &mdash; "The ACME authorization is in a bad state. We need to start over." The ACME challenge path is <i>not</i> the cause: <code>/.well-known/acme-challenge/*</code> reaches the Pages origin untouched through the proxy for both <code>wxyc.org</code> and <code>www.wxyc.org</code>, and there are no CAA records on the domain. Only GitHub can clear this state, and the WXYC org is on GitHub Free, whose support form offers no Pages category &mdash; so the route is GitHub Community Discussions. Full investigation in <a href="https://github.com/WXYC/website/issues/209">#209</a>.</p>
<p><b>Because of that, the Cloudflare SSL/TLS mode must stay on Full (non-strict), not Full (strict).</b> Full (strict) validates the origin certificate, so when the stuck certificate expires the site returns 526 and goes completely offline; under plain Full, Cloudflare still encrypts to the origin but does not validate it, so an expired origin certificate is harmless. This is what keeps the 2026-09-19 expiry from being an outage. Restore Full (strict) only once <code>https_certificate.state</code> reads <code>approved</code> and a certificate with a new serial is confirmed on the origin. <b>#209's original preflight instruction to use Full (strict) is superseded by this note.</b></p>
<p><b>Do not try to fix the certificate by clearing and re-adding the custom domain.</b> This was tested twice &mdash; with an immediate re-add, and with a 20-minute gap &mdash; and GitHub restored the identical <code>bad_authz</code> record both times, so it does not work at any duration. It is also actively harmful: while the domain is detached, Pages returns 404 for the hostname and GitHub's Fastly layer caches that 404 <i>per path</i>, then keeps serving it well past its own <code>max-age</code>. The only purge available is a new Pages deployment &mdash; and since this site normally deploys only when TinaCMS content changes (sometimes a week apart), a poisoned path can stay broken for days. If you must verify something while the domain is detached, probe the origin with a <code>Host:</code> header (<code>curl -k -H 'Host: wxyc.org' https://185.199.108.153/</code>) rather than through Cloudflare, which is what creates the cache entry in the first place.</p>
<p>Two related settings follow from this and should be left alone. <b>Always Use HTTPS is enabled at Cloudflare</b> and is what now serves the http&rarr;https redirect, because GitHub's own <code>https_enforced</code> is stuck <code>false</code> and cannot be re-enabled while the certificate is unissued. And <b><code>www.wxyc.org</code> is redirected to the apex by a Cloudflare Page Rule</b> (<code>www.wxyc.org/*</code> &rarr; <code>https://wxyc.org/$1</code>, 301) rather than by GitHub's www-to-apex canonicalization, so <code>www</code> no longer touches the Pages origin at all.</p>
